From Samples
to Songs

A 39-minute rehearsal is 112,798,720 sample frames. The detector turns them into ten songs with start times, end times and tempos — using no FFT, no spectrogram, no machine learning. Just two running averages and some careful arithmetic. Here is every step of it.

What the whole thing actually does

Everything in audio.py and detect.py exists to answer one question: where does each song start and stop? The trick is that it never tries to answer that from the audio itself. It answers it from two envelopes — cheap summaries of the audio, each a few thousand numbers long — and it makes every decision on those.

That reduction is the whole game. 112 million samples become 23,499 loudness readings, a compression of 4,800×, and every subsequent decision is arithmetic on a small array. This is why the entire inbox analyses in seconds.

And here is what one of your own takes looks like once it has been reduced to that level envelope — 39 minutes of rehearsal as a single line:

01 soundfile audio.py

Audio is just an array of numbers

The single most useful thing to internalise: a WAV file is a short header followed by numbers. The header says how many numbers per second, how many channels they interleave, and how each number is encoded. Everything else in the file is the numbers themselves. soundfile (a binding to libsndfile) is a thin layer that reads that header and hands you the numbers as a numpy array.

Reading the header alone is nearly free

# audio.py — probe()
info = sf.info(path)
return info.samplerate, info.channels, info.frames

sf.info opens the file, parses the header, and stops. It does not read a single audio sample. That is why Take.duration can report the length of five hours of recordings instantly — it is frames / samplerate, pure arithmetic on header fields.

probe -> samplerate=48000 channels=2 frames=112798720 duration = 112798720 / 48000 = 2350.0 s

The conversion that matters: dtype="float32"

# audio.py — _read_file()
with sf.SoundFile(path) as handle:
    handle.seek(int(start_s * handle.samplerate))
    return handle.read(int(duration_s * handle.samplerate),
                       dtype="float32", always_2d=True)

On disk the samples are almost certainly 16- or 24-bit signed integers. Asking for float32 makes libsndfile divide them down into the range −1.0 to +1.0 as it reads. This is worth dwelling on, because it removes an entire category of bugs: you never again care whether a file was 16-bit or 24-bit, and 1.0 always means full scale. Every threshold you write is now expressed against a fixed reference instead of against a bit depth.

read(60.0, 60.05) -> shape=(2400, 2) dtype=float32 min=-0.2828 max=0.2779 first 8 mono samples: [-0.04086 -0.04604 -0.0354 -0.00347 0.0365 0.06031 0.04027 -0.00916]

always_2d=True is the other quiet win. Without it, a mono file returns shape (n,) and a stereo file returns (n, 2), and every downstream function needs a branch. With it you always get (frames, channels), so block.mean(axis=1) is a correct mono downmix for any file, mono included.

The rule

Normalise your input shape and scale at the boundary, once. Every branch you avoid at the edge is a branch you avoid in every function downstream.

A handle you can seek in

sf.SoundFile is a cursor, not a buffer. seek() moves it, read(n) pulls n frames from the current position and advances. That is what makes Take.read(start, end) possible: the review app plays a 12-second preview from the middle of a 39-minute file without ever touching the other 39 minutes. Random access on a 2 GB file, for the cost of a disk seek.

Streaming, so a take is never held in memory

# audio.py — _stream_file()
with sf.SoundFile(path) as handle:
    while True:
        block = handle.read(int(BLOCK_S * handle.samplerate),
                           dtype="float32", always_2d=True)
        if len(block) == 0:
            return
        yield block.mean(axis=1)          # (n, ch) -> (n,) mono

A generator yielding 300-second mono chunks. The peak memory for analysing a 39-minute stereo take is one block — 115 MB as stereo float32, immediately reduced to 58 MB mono — rather than the 902 MB the whole take would occupy. The read() returning a zero-length array is libsndfile's end-of-file signal.

When libsndfile cannot open it

NATIVE = {f".{name.lower()}" for name in sf.available_formats()}

This is the data-driven bit worth stealing. Rather than a hardcoded list of extensions, sf.available_formats() asks the installed libsndfile what it can actually open on this machine. Anything not in that set — your iPhone's .m4a, for instance — is routed through ffmpeg instead:

# audio.py — _stream_file(), the fallback
decoder = subprocess.Popen(
    ["ffmpeg", "-v", "error", "-i", str(path),
     "-f", "f32le", "-ac", "1", "-ar", str(samplerate), "-"],
    stdout=subprocess.PIPE)
with decoder.stdout as pipe:
    while raw := pipe.read(int(BLOCK_S * samplerate) * 4):
        yield np.frombuffer(raw, dtype="<f4")

Read that carefully, because it is the clearest possible illustration of the opening claim. -f f32le tells ffmpeg to emit raw little-endian float32 with no container at all — no header, no metadata, just the numbers, straight down a pipe. And np.frombuffer(raw, dtype="<f4") reinterprets those bytes as a float array without copying them. The bytes in the pipe already are the array's memory.

The * 4 in the read size is because each float32 is 4 bytes; the code asks for bytes and thinks in samples. And the m4a path produces numbers indistinguishable from the WAV path, which is why everything downstream is format-blind.

The rule

Decode at the edge, into one canonical representation, and let the rest of the program know nothing about formats. The choice of representation here — mono float32 at the file's own samplerate — is what lets one code path serve a Zoom H6 and an iPhone.

Takes spread over several files

A Zoom H6 rolls over to a new file at 2 GB, mid-song. Take.read() hides that by treating the parts as one continuous timeline:

for path, (rate, channels, frames) in zip(self.paths, self.probes):
    length = frames / rate
    lo, hi = max(start_s, offset), min(end_s, offset + length)
    if lo < hi:                                   # they overlap
        out.append(_read_file(path, lo - offset, hi - lo, rate, channels))
    offset += length
return np.concatenate(out)

This is plain interval intersection. offset tracks where each file begins on the virtual timeline; max(start, offset) and min(end, offset + length) clip the requested window to that file; lo < hi is the standard "do these two intervals overlap" test. Subtracting offset converts back to a position within the file. A request spanning a rollover simply produces two reads that np.concatenate joins.

Writing, on the way out

# export.py — encode()
sf.write(raw, take.read(song.start, song.end), take.samplerate)

Symmetrical and unremarkable: an array plus a samplerate is a complete WAV file. It is written to a scratch file only so ffmpeg can loudness-normalise and encode it to mp3, then deleted.

02 numpy four idioms
and two traps

The numpy you actually need

There are exactly four array idioms in this codebase. Learn these and you can write most signal-processing code without a loop.

Idiom 1 — reshape into a matrix, reduce along an axis

This is the central trick and it appears three times in nine lines. You have a long 1-D signal and you want one number per fixed-size chunk. Instead of looping, fold the array into a 2-D matrix where each row is a chunk, then reduce along the row axis:

# audio.py — envelopes()
count = len(x) // frame                            # whole frames only
body = x[:count * frame].reshape(count, frame)
power.append((body ** 2).mean(axis=1))         # one number per row

Two details make it work. count = len(x) // frame uses floor division, and the slice x[:count * frame] discards the ragged tail — reshape demands an exact rectangle and will raise otherwise. And .astype(np.float64) before squaring matters: squaring float32 values near 1e-5 loses precision quickly, and these get summed over millions of frames.

Idiom 2 — np.diff is a filter

highpass = np.abs(np.diff(np.concatenate([carry, x])))[:count * frame]
onset.append(highpass.reshape(count, frame).mean(axis=1))

np.diff computes y[n] = x[n] − x[n−1]. That looks like a bookkeeping operation, but in signal terms it is a first-order high-pass filter — a differentiator. Its frequency response is exactly |H(f)| = 2·|sin(π f / fs)|: zero gain at DC, rising toward Nyquist. It suppresses slow changes and amplifies fast ones. A drumstick click is the fastest thing in the room:

Input frequencymeasured gain2·|sin(πf/fs)|effect
50 Hz0.0070.007bass, hum — removed
500 Hz0.0650.065voice, guitar body — suppressed
5 kHz0.6440.643attack transients — kept
20 kHz2.0001.932stick click — amplified

Then np.abs rectifies it (a transient is a transient whether the waveform jumps up or down) and .mean(axis=1) pools it per frame. That three-operation chain — difference, rectify, average — is a complete onset-strength detector. Real onset detectors do this in the frequency domain with spectral flux; this does it in the time domain for a fraction of the cost, and for finding stick clicks it is entirely sufficient.

The carry variable

carry = np.zeros(1, dtype=np.float32)
for x in take.blocks():
    highpass = np.abs(np.diff(np.concatenate([carry, x])))[:count * frame]
    ...
    carry = x[count * frame - 1:count * frame]

Here is the subtlety of streaming any stateful filter. np.diff on n samples returns n−1 values — the difference across each block boundary is lost. Processing a file in three blocks loses two differences, and at exactly the moments most likely to matter. Prepending the previous block's last sample restores them:

whole-file diff : (999,) streamed with carry: (1000,) identical apart from the first sample: True without carry : (997,) -> 2 samples lost at the seams

The rule

Any filter with memory needs its state carried across block boundaries, and the correctness test is always the same: does streaming produce bit-identical output to processing the whole thing at once? If you cannot answer that, you have a bug waiting for a large file.

Idiom 3 — cumsum for rolling windows

# detect.py — rolling_mean()
cumulative = np.cumsum(np.concatenate([[0.0], padded]))
return (cumulative[window:] - cumulative[:-window]) / window

The prefix-sum trick. Once you have a cumulative sum C, the sum of any window is C[i+w] − C[i] — a single subtraction regardless of window width. Computing every window at once is then two array slices. The whole thing is O(n) rather than O(n·w), and it is the reason a 2-second rolling baseline over 470,000 onset points costs nothing:

cumsum : 2.62 ms loop : 180.41 ms (69× slower) max abs difference: 2.62e-15

The prepended [0.0] exists so that cumulative[0] == 0 and the window starting at index 0 works without a special case. The known caveat: over very long arrays, cumulative sums accumulate floating-point error, and subtracting two large nearly-equal numbers loses precision. Here the values are small, positive, and the arrays are hundreds of thousands rather than billions of elements, so the error stays at 1e-15.

Why the median cannot use this

# detect.py — median_smooth()
return np.median(np.lib.stride_tricks.sliding_window_view(padded, window), axis=1)

A median is not a running sum, so there is no prefix trick. Instead sliding_window_view builds a 2-D array whose row i is the window starting at i — and it does so without copying, by manufacturing an array with overlapping strides. A 23,499-point envelope with a 20-point window becomes a (23499, 20) array that occupies no extra memory. Then it is idiom 1 again: reduce along axis=1.

Why a median rather than a mean here? Because a mean is dragged by outliers, and a single loud cough in an otherwise quiet gap would lift the average enough to look like playing. A median ignores it.

Idiom 4 — boolean masks become spans

You have a boolean array marking where something is true, and you want the list of contiguous regions. The idiom is: difference the mask, then find the non-zero positions.

# detect.py — loud_spans()
edges = np.diff(np.concatenate([[0], loud.view(np.int8), [0]]))
spans = [[start * LEVEL_HOP_S, stop * LEVEL_HOP_S]
         for start, stop in zip(np.flatnonzero(edges == 1),
                              np.flatnonzero(edges == -1))]
mask : [0 0 1 1 1 0 0 1 1 0 0 1] edges : [ 0 0 1 0 0 -1 0 1 0 -1 0 1 -1] rises at : [ 2 7 11] falls at : [ 5 9 12] spans : [(2, 5), (7, 9), (11, 12)]

A +1 in the difference is a rising edge, a −1 is a falling edge, and zipping them pairs each start with its stop. Three details earn their place:

  • loud.view(np.int8) reinterprets the boolean bytes as signed integers for free — no conversion, no copy. Without it, np.diff on booleans does XOR and you cannot tell a rising edge from a falling one.
  • The sentinel zeros at both ends are not defensive padding; they are load-bearing. Without the trailing zero, a region still true at the end of the array never produces a falling edge, and the zip silently drops it. Try it on the example above — the span (11, 12) vanishes.
  • Multiplying indices by LEVEL_HOP_S converts array positions back into seconds. Every index in this codebase is an index into an envelope; seconds only appear at the boundaries.

Two traps

Trap 1 — padding a dB array with zeros

padded = np.pad(values, (window // 2, window - window // 2 - 1), mode="edge")

Both smoothing functions pad before windowing, so that the output has the same length as the input and stays aligned in time. The mode is not a stylistic choice. In a dB array, 0.0 means full scale — the loudest sound representable. Padding with zeros tells the smoother that the recording is preceded by the loudest imaginable noise:

mode=edge first value -20.00 dBFS last -20.00 dBFS mode=constant first value -10.00 dBFS last -20.00 dBFS

A 10 dB error at the start of every file, from a default. mode="edge" repeats the first and last real values instead, which says "assume it continued as it was" — the only honest assumption available.

Trap 2 — the logarithm of silence

return 20 * np.log10(np.maximum(level, 1e-10)), np.concatenate(onset)

Digital silence is exactly 0.0, and log10(0) is −inf. One infinity poisons every statistic downstream: means become nan, histograms fail, Otsu returns garbage. np.maximum(level, 1e-10) clamps the floor to −200 dBFS, which is far below anything real and finite. The same pattern appears in _click_peaks as np.maximum(baseline, 1e-12) to avoid dividing by zero.

03 the maths detect.py

The mathematical magic, such as it is

There are five real ideas here. None requires more than secondary-school algebra, and each solves a problem that a naive threshold cannot.

1. RMS and dBFS — measuring loudness

Loudness over a frame is root mean square: square every sample, take the mean, take the square root. Squaring is what makes it work — audio swings symmetrically around zero, so the plain mean of a loud signal is approximately zero. Squaring makes everything positive and, not coincidentally, proportional to energy.

power  = (body ** 2).mean(axis=1)     # mean square — proportional to energy
level  = np.sqrt(power...)            # RMS — back to amplitude units
db     = 20 * np.log10(level)          # dBFS

The 20 rather than 10 is because RMS is an amplitude, and power goes as amplitude squared: 10·log10(A²) = 20·log10(A). Use 20 for amplitudes, 10 for powers. Getting this wrong halves or doubles every threshold in your system.

Why dB at all? Two reasons, and the second is the one that matters for detection:

  • Hearing is roughly logarithmic, so dB differences correspond to perceived differences.
  • A dB difference is gain-invariant. Turn the recorder's input gain up by a factor of two and every RMS value doubles — but every difference in dB is unchanged. This is why rise_db, hysteresis_db and min_class_gap_db all survive a change of recorder or a change of preamp setting, and why an absolute amplitude threshold would not.

The subtle bit: average the power, not the RMS

Look again at where the square root sits in envelopes():

power = np.concatenate(power)                              # mean square @ 5 ms
usable = len(power) // group * group
level = np.sqrt(power[:usable].reshape(-1, group).mean(axis=1))

The 5 ms mean-squares are averaged in groups of twenty, and only then square-rooted. It would be much more natural to compute RMS per frame and average the RMS values — and it would be wrong, because the mean of square roots is not the square root of the mean. Energy adds; amplitude does not.

2. Two resolutions from one pass

The frames are 5 ms; the level envelope groups twenty of them into 100 ms. This is a deliberate split, and it is the same tradeoff you meet everywhere in signal processing: short windows resolve time precisely but measure level noisily; long windows measure level stably but smear time.

Envelopehopratemust resolve
onset5 ms200/sindividual stick clicks, and the ~85 ms room reflection after each
level100 ms10/sonly the shape of a song, over minutes

Rather than making two passes, the code computes at the fine resolution and aggregates down — which is also precisely why the power must be summed before the square root. Pick your hop from the shortest event you must resolve, then aggregate for anything coarser.

3. Otsu's method — letting the data choose the threshold

The hardest question in this system is "how loud is loud?" The answer must be different for every session, because gain, room and band volume all vary. Otsu's method answers it from the data.

Given a histogram of values, consider every possible threshold t. It splits the data into two classes with weights ω₀, ω₁ (the fraction of data in each) and means μ₀, μ₁. Define the between-class variance:

σ²B(t) = ω₀(t) · ω₁(t) · (μ₀(t) − μ₁(t))²

and pick the t that maximises it. Intuitively: choose the split that pushes the two group means as far apart as possible while keeping both groups substantial. It is also equivalent to minimising the variance within the two classes, because total variance is fixed — so the split that best separates the groups is also the split that makes each group most internally consistent.

The implementation is that formula rearranged so every candidate threshold is evaluated at once:

def otsu(values, bins=256):
    histogram, edges = np.histogram(values, bins=bins)
    weights = histogram / histogram.sum()          # probability per bin
    centres = (edges[:-1] + edges[1:]) / 2         # bin midpoints
    mass = np.cumsum(weights)                      # ω₀ for every t
    mean = np.cumsum(weights * centres)            # ω₀·μ₀ for every t
    spread = mass * (1 - mass)                     # ω₀·ω₁
    between = np.where(spread > 1e-12,
                       (mean[-1] * mass - mean) ** 2 / np.maximum(spread, 1e-12), 0)
    return centres[np.argmax(between)]

Two cumulative sums give ω₀ and ω₀·μ₀ for all 256 thresholds simultaneously. mean[-1] is the global mean μT, and the algebra (μT·ω₀ − ω₀μ₀)² / (ω₀ω₁) is the same quantity as the formula above, written to avoid computing μ₁ separately. Idiom 3 again, doing 256 evaluations in two passes.

Run it twice, for three classes

floor = otsu(pooled)                # room silence | everything audible
audible = pooled[pooled > floor]
split = otsu(audible)               # talking | playing

A rehearsal has three states, not two: room silence, talking, playing. Otsu is binary, so it is applied once to strip the silence and again to the remainder. Here is the result on your own session:

Otsu always answers, even when there is no question

This is the failure mode you must guard against. Otsu returns the best split of whatever you give it — including unimodal noise, where no meaningful split exists:

two real classes at -50 and -20 dB -> threshold -39.57 dBFS misclassified: 0 of 4000 quiet, 0 of 6000 loud unimodal noise at -50 dB only -> threshold -50.06 dBFS (it still returns something — there was nothing to find)

Hence Calibration.reliable, which asks whether the classes are far enough apart to be believed, and hence the pooling: calibration runs over every take in the session at once. A single take containing only music has no talking to find, so the split lands inside the music and cuts it in half; a silent rollover file has no music, so the split lands inside the noise floor and invents a music class at −54 dBFS. Both were observed. Pooling guarantees the histogram contains all three classes.

The rule

An algorithm that always returns an answer needs a separate test of whether the answer means anything. Compute the threshold and the confidence in it as two different things.

4. Hysteresis — one threshold is never enough

for index, value in enumerate(db):
    active = value > calibration.exit if active else value > calibration.enter
    loud[index] = active

Two thresholds, four decibels apart, straddling the split: enter = split + 2, exit = split − 2. To turn the gate on the signal must exceed the higher one; to turn it off it must fall below the lower one. This is a Schmitt trigger, and it is the same principle as a thermostat that heats to 21° but does not restart until the room falls to 19°.

After the gate, spans separated by less than min_gap_seconds (15 s) are merged. In image processing this operation is called a closing: fill holes smaller than a given size. Here it says that a four-second pause inside a song is not the end of the song.

5. Finding the count-in

The level gate finds where playing stops, but it is poor at where playing starts — a song with a quiet intro is already a minute old before the level rises. The drummer's four drumstick clicks mark the start exactly. Finding them takes three separate ideas.

Adaptive thresholding

baseline = rolling_mean(onset, tuning.click_baseline_seconds, ONSET_HOP_S)
ratio = onset / np.maximum(baseline, 1e-12)
candidates = np.flatnonzero(ratio > tuning.click_ratio)

The test is not "is this onset large" but "is this onset large compared to its own neighbourhood" — four times the local two-second average. This matters enormously. A global threshold on a file dominated by loud music finds 260 onsets and only 2 real count-ins; the clicks that occur in quiet moments are far below the level of ordinary drum hits during a song. Dividing by a local baseline makes the test scale-invariant: it asks about contrast, not magnitude.

Non-maximum suppression

for index in candidates:
    if peaks and index - peaks[-1] < separation:
        if onset[index] > onset[peaks[-1]]:
            peaks[-1] = index            # keep the stronger one
        continue
    peaks.append(index)

A single click produces a run of consecutive candidates, and about 85 ms later the room's first reflection produces another. Without suppression each click is counted two or three times, and the spacing test that follows collapses. The rule — within click_min_separation_seconds (150 ms, chosen to exceed the reflection) keep only the strongest — is the same idea used to deduplicate bounding boxes in object detection.

Even spacing, plus the level context

Four evenly spaced transients also describes a drummer playing time, and a detector that stops here reports nine overlapping "count-ins" inside one continuous groove. What actually distinguishes a count-in is what surrounds it: quiet before, sustained loudness after.

window = gaps[index:index + 3]                          # three gaps between four clicks
even = (shortest_beat <= window.min() and window.max() <= longest_beat
        and window.max() / window.min() < tuning.evenness)

beat = window.mean()
start, downbeat = times[index], times[index + 3] + beat

before = level_between(start - lead_from, start - lead_to, tuning.lead_percentile)
after  = level_between(downbeat + follow_from, downbeat + follow_to)
if after - before >= tuning.rise_db and after > calibration.floor:

Four points about this test are worth carrying away:

  • Evenness is a ratio, not a tolerance. max/min < 1.22 is scale-free, so the same test works at 53 BPM and at 112 BPM. An absolute tolerance in seconds would be far too loose at one tempo and far too tight at the other.
  • The downbeat is one beat after the last click. "One, two, three, four" — the music starts on the next beat, so times[index+3] + beat. This is why the count-in gives an exact start rather than an approximate one, and why bpm = 60 / beat comes free.
  • The lead window uses the 25th percentile, not the median. The question being asked is "was it quiet at any point in the four seconds before the clicks", not "was it quiet on average". On a restart, the aborted take still occupies part of that window and would drag a median up. Narrowing the window instead was tried, and it lost real detections.
  • The rise is relative. after − before >= rise_db compares the recording to itself. A verified count-in was once rejected by an absolute test because that take's music sat at −35 dB while the session split was −32.7 dB.

Fusing the two detectors

songs() is short because the hard work is done. Each loud span is cut at every count-in inside it; a count-in reaching up to 20 s before the span's start still claims it, which is how a quiet intro gets recovered. Where a span has no count-in, its own edges are used and the song is marked origin="level" — honest about being less precise.

That origin field then drives confidence, which drives what the review app shows you. The system does not pretend to certainty it does not have.

The rule that matters most

Two weak detectors that fail in different ways beat one detector you keep trying to perfect. The level gate is reliable at ends and unreliable at starts; the count-in detector is exact at starts and absent whenever the drummer does not count. Neither would be acceptable alone. Together they cover each other, and where they disagree the disagreement is surfaced as low confidence rather than hidden.

04 reproducing
this

The transferable recipe

Strip away the rehearsal-specific parts and what remains is a method that applies to almost any "find the interesting regions in a long signal" problem — audio, sensor traces, log volumes, telemetry.

  1. Reduce to an envelope before deciding anything. Never make decisions on raw samples. Compute a small summary array first and do all the logic on that. Everything becomes fast, plottable, testable and debuggable, because you can print the whole thing.
  2. Choose the hop from the shortest event you must resolve. 5 ms because a stick click and its 85 ms reflection must be distinguishable. Then aggregate down for anything that only needs coarse resolution, rather than making a second pass.
  3. Work in decibels, ratios and percentiles — never absolute magnitudes. Every threshold that survives a change of microphone, room or gain is a relative one. This single choice is why the same code handles a Zoom H6 and an iPhone with one overridden constant.
  4. Let the data set the threshold. Otsu for a class boundary, a rolling mean for a local baseline, a percentile for "was it ever quiet". A hardcoded threshold is a bug scheduled for the next recording session.
  5. Pool enough data for the statistics to be meaningful. Calibration over a whole session rather than per file, because a single file may contain only one class and the algorithm will happily invent the other.
  6. Always test whether the answer means anything. Otsu returns a threshold even for pure noise. Compute the confidence separately and surface it.
  7. Add hysteresis to every threshold that makes a decision over time. A single comparison chatters. Two thresholds and a state variable cost four lines and remove a whole class of spurious boundaries.
  8. Suppress non-maxima before you measure spacing. Any real-world peak arrives as a cluster — the event, its reflections, its ringing. Collapse each cluster to one peak before any timing analysis, or the analysis is measuring your detector rather than the signal.
  9. Combine independent weak signals rather than perfecting one. Two detectors with uncorrelated failure modes cover each other. Record which one fired, and let disagreement become a confidence level rather than a hidden coin flip.
  10. Validate on real recordings, not synthetic tests. The tests in tests/test_detect.py pin down behaviour you have already decided is correct. They cannot tell you what correct is. Tuning to a fabricated case has already broken real behaviour here once — a narrowed lead window that fixed an invented restart and silently lost a genuine one.

What is deliberately absent

No FFT. No spectrogram. No mel bands, no machine learning, no beat-tracking library. The entire system is built from mean, diff, cumsum, median, histogram and a comparison. That is not a limitation you should feel obliged to fix — it is why five hours of audio analyse in seven seconds, why every intermediate value can be printed and understood, and why when detection is wrong you can find out exactly why.

Reach for the frequency domain when you genuinely need to separate sounds that overlap in time — picking the bass line out from under the drums. For "is anyone playing" and "did someone just hit a stick", the time domain is not merely sufficient, it is the better tool.
